# 第一章｜云计算概论与技术演进

## 1.1 云计算发展主线

**核心结论：**云计算不是单次替换技术，而是资源抽象和自动化不断累积的过程：**资源共享 → 资源虚拟化 → 资源服务化 → 应用云原生化 → 智能算力服务化**。对应技术脉络为大型机分时、互联网/分布式计算、虚拟化、商业云、容器/Kubernetes、Serverless、边缘云与 AI 云。〔第1章，P3–8〕

- **1950s–1960s 思想萌芽：**大型机昂贵，分时系统实现多用户共享；Utility Computing 提出像水电一样按需获得计算能力的设想。重点在“是否必须拥有机器”这一理念转换。
- **1970s–2000s 技术积累：**Internet 提供远程连接；分布式计算实现多机协同；网格计算探索跨机构资源共享；虚拟化提供硬件抽象与隔离。
- **2006–2013 云商业化：**IaaS、资源池化、按需付费、弹性伸缩，基础资源从设备变成标准化云服务。
- **2013–2020 云原生化：**容器标准化交付，Kubernetes 自动编排；微服务、声明式 API、可观测性和持续交付使管理对象从“虚拟机”上升到“应用”。
- **2020–2026 智能云：**CPU/GPU/加速器组成异构资源池；AI Platform、Model Serving、Foundation Model/MaaS 将训练、推理和模型能力服务化。注意：这是课件为便于理解所采用的历史阶段划分，不意味着技术在阶段交替时完全消失。

## 1.2 NIST定义、五大特征与“1+5+3+4”

**NIST SP 800-145 经典框架：**1个核心定义、5项基本特征、3类服务模型、4种经典部署模型。云计算允许用户通过网络便捷、按需地访问可配置的共享计算资源池，资源能够快速提供与释放，所需人工管理和服务商交互很少。按用量计量和付费是云商业模式的重要特征。〔第1章，P9–10〕

| 五大特征 | 含义 | 现代实现或例子 |
|---|---|---|
| 按需自助 On-demand Self-service | 用户自主申请/释放资源，减少管理员人工介入 | 云控制台、API、IaC |
| 广泛网络访问 Broad Network Access | 借助标准网络机制访问云服务 | Web、移动端、API、专线/5G |
| 资源池化 Resource Pooling | 将计算、存储、网络等资源动态分配给多租户 | VM、容器、GPU、存储池 |
| 快速弹性 Rapid Elasticity | 根据业务负载快速增减资源 | Auto Scaling、Kubernetes、Serverless |
| 可度量服务 Measured Service | 对资源使用进行测量、监控、计量 | CPU时间、存储、流量、请求数、GPU时间、Token |

**容易混淆：**资源池化 ≠ 必然自动扩容（还需调度、监控与策略）；可度量服务 ≠ 只能按小时收费；“广泛网络访问”不要求所有云服务都暴露公网。

## 1.3 服务模型与责任边界

**抽象程度逐层升高：**Physical Resources → IaaS → PaaS → SaaS，再扩展到 XaaS。抽象越高，用户越少管理底层组件，越多关注业务。〔第1章，P11；第2章，P7–8〕

| 模型 | 交付内容 | 用户重点管理 | 服务商负责 | 课件中的例子 |
|---|---|---|---|---|
| IaaS | 计算、存储、网络基础资源 | 操作系统、软件、中间件、应用、数据 | 硬件、虚拟化、基础资源 | VM、块存储、VPC、负载均衡 |
| PaaS | 开发、运行、数据库等平台能力 | 应用代码、业务逻辑、数据 | 底层基础设施、平台运行环境 | 应用运行平台、托管数据库、AI训练平台 |
| SaaS | 完整软件产品 | 用户配置与业务使用 | 完整软件及底层技术栈 | 在线办公、CRM、会议/教学系统 |
| XaaS | “各种能力即服务”的统称，不是固定层 | 依具体服务划分 | 依具体服务划分 | CaaS、FaaS、DBaaS、AIaaS、MaaS |

**答题关键：**题目问“控制力强/需要自管OS”选 IaaS；问“专注开发与运行环境”选 PaaS；问“直接使用软件”选 SaaS。XaaS 指服务化趋势，不是与 IaaS/PaaS/SaaS 完全并列的唯一新层。

## 1.4 部署模型、混合云/多云与主权云

| 形式 | 核心含义 | 主要优势/动机 | 要注意的边界 |
|---|---|---|---|
| Private Cloud 私有云 | 为单一组织提供专属云环境 | 强控制、定制、核心业务与合规 | 不等于一定部署在自己机房 |
| Public Cloud 公有云 | 服务商向多用户提供共享云资源池 | 规模经济、服务丰富、快速弹性 | 共享资源需多租户隔离 |
| Community Cloud 社区云 | 面向具有共同需求的组织群体 | 共同策略、合规目标 | 属于NIST经典四种部署模式之一 |
| Hybrid Cloud 混合云 | 连接本地/私有环境与公有云并协同 | 在数据控制与公有云弹性间平衡 | 不只是有两套互不连通的系统 |
| Multi-Cloud 多云 | 使用多个云服务商 | 优势互补、覆盖地区、降低单一供应商依赖 | 与混合云维度不同，二者可同时存在 |
| Sovereign Cloud 主权云 | 将地域、法律管辖、数据主权和运营控制要求落实到云治理中 | 数据驻留、行业监管、运营自主 | 不是简单“国产化”或一种单独硬件架构 |

**混合云 vs 多云：**混合云比较的是**环境类型如何组合并协作**（本地/私有+公有）；多云比较的是**供应商是否有多个**。混合云可只用一家公有云服务商；多云可以没有自建私有云。〔第1章，P12、P17–18；第2章，P9〕

**主权云在架构中的落实：**Jurisdiction/Policy（司法与监管边界）、Identity & Access（身份和权限）、Data Residency（数据驻留）、Encryption/Key Management（加密与密钥控制）、Operations/Audit（运维审计）。这些能力跨越资源、平台和治理层；具体形态可建立于私有云、公有云或混合云之上。〔第1章，P21–22〕

## 1.5 Cloud Native、Serverless、Edge Cloud与AI Cloud

**Cloud Hosted vs Cloud Native：**Cloud Hosted 只是把既有应用放上云 VM；Cloud Native 使用容器、微服务、声明式管理、编排、自动化交付和可观测性，针对云平台的弹性、分布式和动态环境重新设计应用。课件将 Containers、Microservices、Orchestration、DevOps/CI-CD、Observability、Serverless 视为云原生体系的重要技术要素。〔第1章，P13–14〕

**云原生交付运行闭环：**Code → Build → Package（容器镜像）→ Deploy → Orchestrate（Kubernetes编排）→ Observe（Metrics/Logs/Traces）→ Feedback（反馈改进）。容器解决“一致交付”；微服务解决“独立演进”；Kubernetes 解决“大规模自动编排”；Service Mesh 解决“服务通信治理”；可观测性解决“复杂系统如何诊断”。

**Serverless：**VM → Container → Function/FaaS 表示计算资源的抽象层次上升，而不是 VM/容器完全被替代。典型流程 **Event Sources → Event Trigger → Function/FaaS → Managed Runtime/Scaling → Result/Downstream Services**。开发者主要提交函数代码及配置，平台负责服务器、运行时、弹性和生命周期；“无服务器”指使用者无需直接运维底层服务器，并非物理服务器不存在。适合事件触发、间歇请求等业务，需关注事件执行模式和平台管理边界。〔第1章，P15–16〕

**Edge Cloud：**Devices（设备采集）→ Edge Nodes（就近处理/缓存/推理）→ Cloud（全局分析/训练/集中治理）；优势是降低回传时延、带宽开销并支持数据本地性，不能脱离边缘算力、链路和运营条件判断性能。〔第1章，P19；第6章〕

**AI Cloud：**GPU/Accelerator → 高速网络与分布式训练/存储 → AI Platform → Model Serving → MaaS/API → AI Application。对模型训练与推理，普通 VM 数量不是唯一决定因素；还需 GPU、集群调度、高性能网络与存储、模型运维及推理弹性。〔第1章，P20〕

## 1.6 现代云技术栈、挑战与综合分析

课件中的现代技术栈含 **Compute、Storage、Network、Container、Data、AI、Platform Services** 七类能力：Compute含VM/GPU；Storage含块/文件/对象；Network含VPC/LB/SDN；Container含Runtime/Kubernetes/Service Mesh；Data含数据库、湖仓、流处理、向量库；AI含GPU Cloud、Model Service、RAG、Agent；Platform Services含API Gateway、IAM、DevOps、Observability。〔第1章，P23〕

**现代云治理的新挑战：**从资源安全延伸到身份/权限（IAM、最小权限、Zero Trust）、数据加密与隔离、合规/主权、成本与业务价值、云原生及多云复杂性、可靠性/可观测性，以及AI模型、数据与智能体治理。〔第1章，P24〕

**课堂综合题（企业多模态AI助手）：**从四个角度说明“为何不能只租几台VM”：①资源—需要异构GPU、存储与网络；②平台—需要容器编排、AI平台、RAG与模型部署；③成本—按负载弹性、计量与治理；④部署—多环境和未来云—边—端协同，按时延/隐私/带宽/算力选择计算位置。〔第1章，P25–26〕

# 第二章｜现代云计算与云原生体系结构

## 2.1 传统五层与现代六层：两种看系统的视角

**传统五层云计算体系结构：**应用层、平台层、资源层、用户访问层、管理层。着重从资源到应用的服务封装：抽象物理差异，封装数据库/消息队列等能力，通过Web/API交付；管理层提供运行与治理。局限是更偏向静态的“层次关系”，难描述持续调度、状态协调和自动修复。〔第2章，P5–6〕

**现代云平台为什么要换视角？**虚拟化云的主要对象是VM和资源池；容器云关注容器实例；云原生进一步关注调度、弹性、服务通信、可观测和自动化；AI Cloud 还要管理GPU、模型和AI应用。现代平台是**可编程、可自动化的运行体系**。〔第2章，P3–4〕

## 2.2 服务交付、多租户、资源池化与SLA

**多租户（Multi-tenancy）：**多个客户共享同一底层资源，逻辑隔离其数据、安全与管理边界。与“多用户登录同一应用”相比，多租户要求明确租户间的隔离与治理。〔第2章，P10–11〕

| 多租户模式 | 共享方法 | 隔离/成本的典型特点 |
|---|---|---|
| Silo | 租户独享应用和数据库等资源 | 隔离较强，成本高、利用率低 |
| Pool | 多个租户共享计算、应用甚至数据库 | 资源利用率高，但安全隔离设计更复杂 |
| Bridge | 有些层共享，有些层独享 | 在成本与隔离之间折中 |

**资源池化：**把多个服务器/存储/网络/GPU 的可用容量汇聚成可调度资源池，而不是某个租户永久独占某台设备。是弹性伸缩基础，但弹性还需要监控、调度、自动化机制。〔第2章，P12〕

**服务交付：**API、Console、SDK、CLI 为统一的资源申请/访问入口，将资源或平台能力标准化地交付。〔第2章，P13〕

**SLA（Service Level Agreement）：**服务商和用户之间对服务范围、服务指标、目标值、统计方式、适用条件与违约补偿的约定。要区分 SLA 的协议责任，与 SLI 的测量指标及 SLO 的内部/工程目标。课件用 Availability、Latency 等作为服务指标示例。〔第2章，P14；第5章 P16〕

## 2.3 现代六层云平台架构：逐层职责

**总体主线：**硬件 → 运行环境 → 资源编排 → 云原生基础设施 → 平台服务 → 应用/AI；抽象程度逐层升高。〔第2章，P15–22〕

| 层次 | 主要内容 | 核心要回答的问题 |
|---|---|---|
| Layer 1 Physical Infrastructure | CPU、内存、GPU/AI加速器、物理存储与网络 | 底层有哪些计算/存储/网络能力？ |
| Layer 2 Virtualization & Container Runtime | Hypervisor/VM、容器运行时、vGPU/MIG | 应用以何种隔离运行单元执行？ |
| Layer 3 Resource Orchestration | Scheduler、Container Orchestration、Auto Scaling | 应用在哪里运行、开多少实例、故障后如何恢复？ |
| Layer 4 Cloud-Native Infrastructure | Kubernetes周边的运行、服务治理、可观测、自动化 | 多服务系统如何持续可靠地运行？ |
| Layer 5 Platform Services | Database、Big Data、AI Platform、MaaS、API Services | 如何把复杂能力包装成开发者可调用的服务？ |
| Layer 6 Application / AI Application | Microservices、Web App、AI App、Agent | 最终为用户提供什么业务和智能能力？ |

**逐层理解：**第1层供给原始硬件能力；第2层在硬件与OS/应用之间做隔离、封装与运行；第3层将资源池变成能按需运行工作负载的可调度平台；第4层治理应用在动态分布式环境中的生命周期；第5层暴露数据库、流处理和模型 API；第6层承载业务应用。与传统五层并不是“简单增加一层”，而是按运行职责重新划分。〔第2章，P16–22〕

## 2.4 微服务、Docker与云原生的架构演进

**传统稳态IT vs 敏态IT：**稳态重稳定、安全与性能；敏态面临互联网、AI、IoT、移动端的需求快速变化，需要敏捷、弹性和灵活交付。应用数量、类型与变化速度增加，推动从单体向微服务演进。〔第2章，P24–27〕

**微服务：**在服务化思想上把复杂应用拆成较细粒度、能独立开发、部署、扩缩容和管理的服务；服务之间通过轻量通信机制协作（课件举REST），每个服务可根据需要选择技术/数据存储。优势是独立交付、故障影响范围可控、技术演进灵活；代价是服务发现、跨服务通信、链路故障、配置管理与追踪变复杂。〔第2章，P28–29〕

**Spring Cloud传统生态例子：**Eureka（注册与发现）、Hystrix（熔断）、Config/Bus（配置与变更通知）、Zuul（网关）、Sleuth/Zipkin（请求追踪）。这些是课件用于说明服务治理功能的组件示例，不必理解为当前必须选择的唯一实现。〔第2章，P29〕

**Docker三项基本概念：**Image 镜像为打包了应用及依赖的模板；Container 容器是镜像启动后的运行实例；Registry 镜像仓库负责存放与分发镜像。Docker 引擎通常遵循 Client/Daemon 架构；容器使环境可移植、便于微服务部署，但微服务数量巨大时还需要编排。〔第2章，P30–33〕

**为什么“微服务+VM”仍不够？**资源预分配、扩容速度、服务隔离、端口与网络配置、监控粒度和发布维护等问题会持续存在。云原生进一步把 **微服务的业务适应性 + DevOps持续交付 + 可自动变化的技术底座** 组合起来，以应对不断变化的业务和技术环境。〔第2章，P31–33〕

## 2.5 Kubernetes：概念、对象、组件、控制/数据平面

**定义：**Kubernetes（K8s）用于自动部署、扩缩容和管理容器化应用；通过声明式 API 记录对象的期望状态，控制器持续协调实际状态。**不是只负责启动容器，也不是 Docker 的同义词。**〔第2章，P34〕

**基本对象：**Pod 是最小可部署计算单元，可包含一个或多个容器；Manifest（通常YAML）声明对象配置；Service 提供访问和服务发现抽象；Namespace 提供资源逻辑分组与隔离；Node 是集群级对象，不属于某个命名空间；CRD 允许扩展自定义资源类型。裸 Pod 若缺少控制器，不具备 Deployment 等控制器的期望副本维护机制。〔第2章，P35–44〕

**控制平面（Control Plane）：**

| 组件 | 作用与典型行为 |
|---|---|
| kube-apiserver | Kubernetes统一REST API入口，承担请求处理、身份认证/授权/审计，与etcd持久化集群状态；课件列默认端口6443 |
| etcd | 强一致性的复制键值存储，用于保存资源对象与集群状态；其复制与选举使用Raft |
| kube-scheduler | 观察未绑定Node的Pod，综合资源需求、亲和性、约束、负载等选择节点 |
| kube-controller-manager | 持续对比期望状态与实际状态，执行Reconcile，例如异常副本替换、状态收敛 |
| cloud-controller-manager | 连接云厂商API，协调节点、路由、负载均衡等云基础设施（课件架构图备注提及） |

**工作节点（Worker Node）：**

| 组件 | 作用与典型行为 |
|---|---|
| kubelet | 在节点上监控并管理Pod生命周期，调用容器运行时、报告状态并注册节点 |
| Container Runtime | 负责镜像与容器运行，如containerd、CRI-O；通过CRI与kubelet协作 |
| kube-proxy | 根据Service实现网络转发规则与流量分发（如iptables相关机制） |
| CNI | 容器网络接口规范，供插件配置Pod网络；与Service转发职责不同 |

**典型部署路径（简答题可以按此写）：**①用户 `kubectl apply` 发送声明式 Manifest → ②API Server 完成准入并写入 etcd → ③Controller 发现期望副本/新Pod → ④Scheduler 为待调度Pod选择Node → ⑤目标节点kubelet通过Runtime创建容器并配置网络 → ⑥状态上报和控制器持续核对 → ⑦Service/kube-proxy与CNI共同支持工作负载通信。〔第2章，P45–58〕

**etcd/Raft联动：**etcd保存K8s关键状态；Raft通过Leader/Follower、复制日志和多数派提交提供强一致基础。课件描述Follower处理线性一致性读时的ReadIndex路径：Follower向Leader确认可读取的提交索引，待本地Applied Index达到要求后再返回数据。〔第2章，P48〕

**控制平面 vs 数据平面：**控制平面决定“应该有几个Pod、部署在哪里、需要什么规则”；数据平面在节点上实际运行Pod并执行请求转发。**声明式 ≠ 运行一次命令就结束**，而是控制器反复使实际状态趋近目标。〔第2章，P56–58〕

## 2.6 Service Mesh、Istio、Sidecar

**Service Mesh为何出现？**微服务通信需要流量管理、安全、重试/超时、熔断和链路遥测；把这些跨服务能力交给基础设施治理，避免在每个业务服务重复实现。〔第2章，P59–61〕

- **Data Plane（数据平面）：**Sidecar/Envoy 等代理直接处理东西向服务流量，执行路由、负载均衡、mTLS、限流和遥测采集。
- **Control Plane（控制平面）：**集中管理策略和代理配置，维护服务路由规则，将配置下发给数据平面；Istio是课件采用的典型服务网格示例。
- **四类典型能力：**Traffic Management（路由、流量拆分、负载均衡、重试/超时）、Security（mTLS、身份认证授权）、Reliability（熔断与故障处理）、Observability（指标、日志、追踪）。

**区别：**API Gateway 重点管理外部进入系统的南北向流量；Service Mesh 更强调服务与服务之间的东西向调用治理；Kubernetes Service 主要提供发现与访问抽象，不能与完整网格治理画等号。

# 第三章｜分布式技术原理与计算框架

> **范围提醒：**课件封面为“分布式技术原理与计算框架”，虽然上传文件名是“第三章分布式存储”，实际覆盖分布式存储、分布式计算、分布式数据管理和 Leader Election；第1部分“分布式系统基本原理”主要是分节引入，没有展开完整的CAP/Paxos专题。〔第3章，P1–4〕

## 3.1 为什么需要分布式存储？

单机存储同时受**容量、吞吐、可靠性、规模扩展**限制。分布式存储通过多个节点协同：①水平增加存储容量；②并行I/O提升吞吐；③多副本/冗余机制提高可用性与容错；④用统一的命名空间和元数据屏蔽物理分布位置。其代价是网络、节点故障、元数据、一致性和运维复杂性。〔第3章，P5〕

| 概念 | 回答的问题 | 基本动作 | 最主要价值 |
|---|---|---|---|
| Block 数据块 | “文件/数据怎么切？” | 大文件拆成固定大小的块 | 便于分布存储和并行访问 |
| Partition 分区 | “数据放到哪里？” | 不同块/记录分布到节点或机架 | 容量扩展与负载分担 |
| Replication 副本 | “数据或节点坏了怎么办？” | 多个节点保存冗余副本 | 容错、读取可用性 |

**不能混用：**Block 是切分粒度，Partition 是放置策略，Replication 是冗余保护。它们可以同时使用，但不是同一概念。〔第3章，P6–7〕

## 3.2 HDFS定位、架构与NameNode/DataNode

**HDFS（Hadoop Distributed File System）：**借鉴 GFS 思想，依靠普通服务器集群提供面向**海量大文件、高吞吐、容错**的分布式文件存储；适合顺序读写和离线批处理，不以低延迟随机行级更新为目标。〔第3章，P8〕

| 角色 | 主要职责 | 与数据路径的关系 |
|---|---|---|
| NameNode | 保存文件系统命名空间、目录、文件→Block、Block→DataNode的元数据；依据副本策略选择节点 | 回答“数据在哪里”，不承担普通文件块的主要传输 |
| DataNode | 实际保存Block；处理读写、复制、删除；报告状态与心跳 | 客户端数据流主要经过DataNode |
| Client | 根据NameNode返回的元数据找到块与节点，直接向DataNode读/写数据 | 负责发起访问、组装/传递块 |

**架构核心：元数据路径和数据路径分开。**客户端先咨询NameNode的位置/分配信息，然后与DataNode传输数据；否则所有文件流经NameNode易形成瓶颈。〔第3章，P9〕

### HDFS写文件（按步骤答题）

1. Client调用HDFS API 请求创建文件；NameNode检查名称空间、权限及文件状态，建立元数据。
2. Client请求写入位置；NameNode按副本放置策略返回多个DataNode。
3. Client把数据分包，送往第一个DataNode；后者通过**pipeline**转发到第二个/第三个DataNode，形成多个副本。
4. 各DataNode写入后沿pipeline回送确认，Client接收ACK，继续后续数据块。
5. 所有数据写完后关闭文件，NameNode完成元数据状态更新。

**易错：**副本写入并不是Client同时向全部节点单独发送同样的数据；课件使用**流水线复制**。〔第3章，P10〕

### HDFS读文件（按步骤答题）

1. Client通过`open()`/`DistributedFileSystem`请求打开文件。
2. 向NameNode查询该文件的Block及各副本的DataNode位置。
3. Client依据位置和距离，选择合适/较近的DataNode，与其直接通信读取块。
4. 读取后续块时按照元数据依次选择对应DataNode；如某副本异常，可改用其他副本。
5. 读取完成关闭文件。NameNode负责元数据定位，不在正常数据读取的主传输路径上。〔第3章，P11〕

### 容错机制：副本、心跳、恢复与纠删码

| 机制 | 说明 |
|---|---|
| Replication | 为每个Block保存多个副本；节点故障后仍可访问其他副本 |
| Heartbeat | DataNode定期上报存活状态；超时可判定为失效节点 |
| Block Report | 上报所持有的Block信息，供NameNode掌握副本分布 |
| Re-replication | 副本数不足时重新复制，以恢复目标冗余水平 |
| Rack Awareness | 副本分布考虑机架，以避免同机架共同故障造成全部副本失效 |
| Erasure Coding | 把数据拆成数据块与校验块，以编码冗余替代完整多副本中的部分空间消耗；在存储效率与计算/恢复成本之间权衡 |

**副本与纠删码比较：**副本实现直观，读取和恢复容易，但冗余空间开销较大；纠删码能以更少冗余存储提供一定容错，但编码解码、恢复时计算和网络读写更复杂。课件用它们说明分布式容错的不同权衡。〔第3章，P12–13〕

## 3.3 数据本地性与DFS案例

**Data Locality（数据本地性）：**将任务尽量调度到数据所在位置或其附近执行，避免移动海量数据。典型优先顺序是 **Node-local → Rack-local → 更远位置**，本地资源不足时再退化到同机架/远程节点。此原则是 HDFS 与 MapReduce 配合的重要原因。〔第3章，P14〕

**淘宝DFS示例：**Client、Master/元数据、Storage Node、文件块与副本共同形成“统一命名空间+分块+多节点存储”架构。案例的重点不是记住商业系统每个名字，而是理解客户端操作逻辑文件时如何由元数据层定位实际块。〔第3章，P15〕

## 3.4 MapReduce：模型、执行流程、Word Count、局限

**MapReduce：**面向大规模数据集的并行计算模型。开发者指定 `map(k,v) -> list(k',v')` 和 `reduce(k', list(v')) -> result`；运行框架负责**数据拆分、任务调度、数据本地性、Shuffle/排序、失败重试和结果写入**。〔第3章，P17–20、P32–35〕

**三段式记忆：Map → Shuffle → Reduce**。

1. **Map阶段：**把输入文件划分为多个Input Split，每个Map Worker读取记录，调用自定义Map函数输出中间键值对。
2. **Shuffle阶段：**按Key进行分区（Partition），把同一Key的中间结果传向同一个Reduce任务，并进行排序/分组；这是跨节点通信的重要阶段。
3. **Reduce阶段：**对每个Key的值集合执行汇总、统计或其他合并逻辑，输出到分布式文件系统。

**完整版运行流程：**用户提交作业→Master管理Worker与任务→分发Map任务→本地读取Split→生成中间键值对→按分区规则写入/传输中间结果→Reducer拉取、合并并排序→调用Reduce函数→写入最终输出。传统图示中Master/Worker是任务协调示意，实际在YARN架构下的资源管理另有分工。〔第3章，P19–20〕

**Word Count例题：**输入文本“a b a”可由Map输出`(a,1),(b,1),(a,1)`；Shuffle后是`a→[1,1]，b→[1]`；Reduce求和得到`(a,2),(b,1)`。各Map局部统计后，仍要按Key把分散结果汇聚；多个节点独立HashMap并不能直接得到完整全局频次。〔第3章，P21–34〕

```text
map(key, documentText):
    for each word in documentText:
        emit(word, 1)

shuffle/group:
    group all values by the same word

reduce(word, counts):
    emit(word, sum(counts))
```

**MapReduce六大特点：**分而治之、并行计算、数据本地性、自动任务调度、故障后重执行、横向扩展。开发者写业务逻辑，框架处理分布式执行复杂度。**局限：**频繁把中间结果写磁盘，迭代式作业效率不高；Map/Reduce表达模式有限；复杂多阶段、低延迟、交互与持续流处理不够合适。〔第3章，P35、P39〕

## 3.5 Hadoop 1.x与YARN

**Hadoop 1.x：**JobTracker负责资源、调度、监控等多项职责，容易形成瓶颈；TaskTracker在节点上执行任务；Map/Reduce Slot分配比较僵化，并与MapReduce模型耦合，不利于其他计算框架。〔第3章，P36〕

**YARN改进思想：将资源管理与每个应用的执行协调分离。**〔第3章，P37〕

| YARN组件 | 职责 |
|---|---|
| ResourceManager（RM） | 集群级统一资源管理与Container资源分配 |
| ApplicationMaster（AM） | 每个应用自己的协调者；向RM申请资源、管理任务执行 |
| NodeManager（NM） | 节点级资源管理、Container创建/监控、状态汇报 |
| Container | 资源分配和执行的基本单元，携带CPU/内存等资源约束 |

**YARN六步执行：**①Client向RM提交应用；②RM先分配一个Container，NM启动AM；③AM按任务需求向RM申请更多Container；④AM联系对应NM启动Map/Reduce等任务；⑤任务并行执行，AM监控进度、NM汇报节点状态；⑥完成后AM注销应用、释放Container，输出结果写入HDFS等持久存储。**不要说所有计算都由RM执行。**〔第3章，P38〕

## 3.6 Spark 与 Flink，以及三大框架对比

**Spark核心机制：**应用计算转换形成DAG；DAGScheduler依据依赖关系将Job切成Stage，遇到Shuffle等宽依赖通常形成Stage边界；每个Stage又分解为Task，由TaskScheduler分配给Executor。Cache/Persist使中间数据可被复用；RDD Lineage支持故障重计算。支持SQL/DataFrame、机器学习、ETL及流式工作负载。**不是所有Spark计算都在内存**：Shuffle、溢写与持久化仍可能访问磁盘。〔第3章，P39–40〕

**Flink核心机制：**持续Dataflow（Source→map/keyBy/window等算子→Sink）；支持Event Time（事件发生时间）与Watermark（为乱序事件处理提供时间进度依据）、有状态算子（State）、Checkpoint（一致性状态快照与故障恢复），并可用统一流模型处理有界/无界数据。〔第3章，P39、P41〕

| 维度 | MapReduce | Spark | Flink |
|---|---|---|---|
| 定位 | 海量离线批处理 | 通用数据分析、复杂DAG与迭代计算 | 有状态、低延迟持续流处理 |
| 计算结构 | Map–Shuffle–Reduce | DAG及Stage/Task | 连续Dataflow |
| 运行方式 | 批作业 | DAG分阶段执行 | 流水线持续执行 |
| 中间结果 | 依赖磁盘持久化较多 | 可以缓存，也会落盘 | 流式数据与状态存储 |
| 流处理 | 传统模型不支持原生持续流 | Structured Streaming（课件强调默认微批） | 原生连续流处理 |
| 状态/时间 | 主要靠应用逻辑 | 可支持有状态处理 | 状态管理、Event Time/Watermark更突出 |
| 容错 | 失败任务重试 | Lineage、重算、Checkpoint | Checkpoint及状态恢复 |
| 例子 | 离线日志统计 | SQL分析、迭代机器学习 | 实时风控、监控、事件窗口 |

**选型原则：**大文件离线批处理→MapReduce可用；复杂DAG和内存复用→Spark；需要连续处理、事件时间、乱序和长期状态→Flink。〔第3章，P42〕

## 3.7 Bigtable：数据模型、架构、读写、Row Key设计

**为什么出现Bigtable？**HDFS擅长大文件顺序访问，却不擅长在线低延迟随机访问、海量小文件和结构化索引；Bigtable提供大规模、分布式、有序的多维映射存储，面向可按键快速定位的在线数据。**Bigtable不是把HDFS改名，也不是关系型数据库。**〔第3章，P44〕

**数据模型：**`(Row Key, Column Key, Timestamp) → Value`。Row Key按字典序排列；列按Column Family（列族）管理，具体列可以动态出现；Timestamp使同一单元格保存多个版本；稀疏表示意味着不存在的列无需占位。〔第3章，P45、P51〕

| 概念 | 定义与作用 | 答题记忆 |
|---|---|---|
| Row Key | 唯一定位行并决定整体排序、范围查询和数据局部性 | “行怎么排列、查询走哪条路” |
| Column Family | 列的逻辑分组与管理单元；可关联访问/保留策略 | “相关列怎么分组” |
| Column Qualifier | 列族中的具体列名 | “哪一列” |
| Timestamp | 单元格的版本标记 | “哪个时刻/版本” |
| Tablet | 按连续Row Key范围切出的数据分片 | “数据在哪个分片上” |

**经典架构：**Master管理Tablet分配、节点变更、负载均衡与故障恢复；Tablet Server负责处理其Tablet上的客户端读写；Tablet按行键区间切分；GFS用于持久化SSTable/日志；Chubby提供协调与锁等能力。课件特别提醒：Master主要负责控制管理，普通读写通常直接访问Tablet Server。〔第3章，P46〕

**经典写路径：**客户端根据元数据定位Tablet Server → 写入Commit Log/WAL（持久化）→ 更新内存有序结构MemTable → 达到阈值时Flush为SSTable持久化文件 → 后台Compaction合并SSTable并清理旧版本。〔第3章，P47〕

**经典读路径：**定位目标Tablet → 从MemTable与SSTable等查找/合并对应单元格版本 → 返回满足请求的结果。Bloom Filter可避免不必要的SSTable探测，缓存减少部分读取开销。节点故障后Master可重新分配Tablet，利用日志和持久化文件恢复。课件讲解备注还用Root Tablet→Meta Table→User Tablet解释经典层级元数据定位。〔第3章，P47〕

**Schema最重要的设计原则：Query Pattern → Row Key → Data Layout。**先问业务最常执行什么查询，再决定Row Key、列族和数据分布，而不是照搬关系数据库范式。Bigtable提供同一行内的原子操作边界，但不提供通用的跨行事务能力；不依赖传统SQL JOIN。〔第3章，P48〕

**Row Key示例与取舍：**

- 要查询设备 `devA` 的一段历史记录，可以考虑 `devA#日期时间`，同设备记录按前缀相邻，便于范围扫描。〔第3章，P49〕
- 用不断递增的时间戳或订单ID作为统一前缀，可能使新写入集中到相邻Tablet，形成热点；即使节点很多，也无法充分均衡写流量。〔第3章，P50〕
- 哈希前缀、分桶、键重排可分散热点，但会牺牲部分连续范围扫描/数据局部性；不能“为了均衡而无目的地全量哈希”。〔第3章，P50、P52〕
- 列族按访问模式、保存周期进行组织；控制列族与大行规模，结合Timestamp设置保留版本及垃圾回收。多租户可把租户ID放入复合行键，但大租户本身仍可能出现热点。〔第3章，P51–52〕

**Bigtable与HDFS比较：**HDFS主要提供文件和块的持久化；Bigtable提供以有序行键/列族为核心的结构化访问模型；下层可靠文件存储与上层在线数据组织可以协同工作，而非只能二选一。

## 3.8 Leader Election：Bully、Ring、Raft

**为什么要选Leader？**协调任务分配、请求顺序或控制状态；Leader故障后需要重新选举。网络分区可能产生脑裂，需通过任期、多数派、租约/Fencing等防止互相冲突的写入。**Leader是逻辑协调者，不代表必须由一台永不变更的物理服务器承担。**〔第3章，P54〕

### Bully（霸道选举）

1. 假设各节点唯一ID、了解成员信息、能检测Leader故障。
2. 发现Leader失效的节点向比自己ID大的节点发送`Election`。
3. 更高ID节点存活则回复`OK`，并继续向更高ID发起选举。
4. 某节点向所有更高ID节点发消息却无人回应，宣布自己为新Leader。
5. 广播`Coordinator`，通知所有节点。

**结果：**存活节点中最大ID的节点当选；实现直观，但最坏消息量可达 O(n²)。〔第3章，P55〕

### Ring（环形选举）

节点形成逻辑环；任意节点发现Leader故障后发送`Election`消息，沿环传递并收集存活节点ID；回到发起者后选最大ID；再用`Coordinator`消息沿环公告。简单单向环的典型消息规模为 O(n)，但必须知道如何绕过失效后继节点。〔第3章，P57〕

### Raft Leader Election（领导者选举）

1. 节点通常作为**Follower**等待Leader的心跳`AppendEntries`。
2. 超时后进入**Candidate**、增加`Term`、投自己一票并发送`RequestVote`。
3. 各节点根据Term及候选者日志新旧情况等条件决定投票，每个Term最多投一票。
4. Candidate获得**超过半数**的票成为Leader；票数冲突时等待新的随机超时重试。
5. Leader持续心跳维持任期；观察到更高Term时退回Follower。

**Raft的不同之处：**不仅是选“最大ID”，还要与日志复制及安全性配套；随机超时减少选举冲突，多数派限制脑裂情形下同时产生可提交写入的Leader。〔第3章，P56〕

| 维度 | Bully | Ring | Raft |
|---|---|---|---|
| 选Leader条件 | 存活节点ID最大 | 存活节点ID最大 | Term内获得多数派投票且满足日志条件 |
| 通信方式 | 向更高ID节点请求和等待OK | Election与Coordinator沿逻辑环传播 | RequestVote、心跳、任期 |
| 简单复杂度表述 | 最坏 O(n²) 消息 | 典型 O(n) 消息 | 一轮典型 O(n)，冲突时重试 |
| 关键限制 | 成员可知和超时检测 | 逻辑环、后继可达性 | 多数派、持久化选举状态及日志安全 |

〔第3章，P58〕

# 第四章｜虚拟化技术

## 4.1 虚拟化的本质、优势和分类

**虚拟化定义：**利用软件和/或硬件支持，将CPU、内存、存储、网络等物理资源抽象成可配置、可隔离、可共享的逻辑资源，为多个工作负载提供独立的运行环境。虚拟化不等于“把服务器远程控制”，也不只等于“装一台VM”。〔第4章，P4–6〕

**核心机制：**①Abstraction资源抽象：vCPU/vDisk/vNIC等统一接口与物理硬件解耦；②Isolation资源隔离：执行上下文、地址空间和设备访问权限分离；③Resource Sharing/Multiplexing资源复用：多虚拟机通过调度和复用共享有限硬件。〔第4章，P6〕

**优势与代价：**提升资源利用率、快速创建模板实例、弹性供给、隔离、多租户运维、迁移/快照/恢复；代价包括虚拟化开销、超分配引起争用、资源隔离并非绝对、管理及故障域复杂。**虚拟化提供资源抽象，云平台还需要调度、镜像、租户、计量、运维、API才构成可交付云服务。**〔第4章，P11–12〕

| 分类维度 | 类型 | 区分原则 | 例子/提示 |
|---|---|---|---|
| 指令/硬件实现机制 | 软件模拟 | 用解释/翻译方式模拟目标CPU与设备行为 | 可用于跨架构，开销可能高 |
| 同一维度 | 硬件辅助虚拟化 | VM可原生执行大量指令，敏感事件受VT-x/AMD-V管理 | 降低关键执行开销 |
| Guest协作程度 | 全虚拟化 | Guest通常无需针对虚拟化专门修改 | 标准硬件接口 |
| 同一维度 | 半虚拟化 | Guest采用Hypercall/专用协作驱动 | Virtio典型地用于I/O |
| 虚拟化层次 | 硬件级虚拟化 | 每个VM具备独立Guest OS与内核 | 服务器VM |
| 同一维度 | 操作系统级虚拟化 | 容器共享宿主内核，隔离进程环境 | Linux容器 |
| Hypervisor位置 | Type 1 | Hypervisor直接或紧密管理物理硬件 | ESXi、Xen、Hyper-V等课件示例 |
| 同一维度 | Type 2 | 作为宿主OS上的程序/服务运行 | 适合开发、测试、教学 |

**特别易错：**“全虚拟化/半虚拟化”判断Guest是否需要协作接口；“软件模拟/硬件辅助”判断指令执行如何实现；“Type1/Type2”判断Hypervisor所在层。这些分类是**不同维度**，不是同一列表的互斥备选。〔第4章，P7–10〕

## 4.2 CPU虚拟化：vCPU、特权级、VM Entry/Exit

**vCPU vs pCPU：**vCPU是Guest可见的虚拟处理器抽象；pCPU是宿主物理执行资源。一个vCPU不意味着长期占用一个物理核。Hypervisor/宿主系统把多个vCPU执行上下文调度到有限pCPU；vCPU总数超过物理逻辑CPU数量称CPU超分配（Oversubscription），前提是负载错峰，风险是CPU就绪等待、争用与性能抖动。〔第4章，P14–16〕

**Intel VT-x中的两个维度：**VMX Root通常执行Hypervisor/宿主虚拟化控制；VMX Non-root允许Guest执行。**Root/Non-root不等于Ring 0/Ring 3**：Guest内核仍可以在Non-root环境中的Ring 0执行，Guest用户程序通常在Non-root的Ring 3执行。〔第4章，P17〕

**VM Entry与VM Exit：**

1. Hypervisor准备VM执行状态、控制结构；通过VM Entry进入Guest执行（课件列VMLAUNCH/VMRESUME）。
2. Guest大量普通指令可直接运行，CPU按虚拟化控制条件监视特殊操作。
3. Guest执行指定的I/O/敏感操作或触发其他退出条件时，CPU执行**VM Exit**并切回Hypervisor处理。
4. Hypervisor完成模拟/设备处理/权限检查后，再次VM Entry恢复Guest。

**性能启示：**频繁Exit/Entry存在切换成本；硬件辅助虚拟化的意义是减少必须完全通过软件模拟的路径，并不表示所有操作零开销。〔第4章，P18〕

## 4.3 典型平台：QEMU/KVM、Xen、Hyper-V

| 平台 | 基本架构 | 重点记忆 |
|---|---|---|
| QEMU/KVM | KVM位于Linux内核中，利用CPU虚拟化能力；QEMU运行在用户空间，管理VM进程并提供设备模型/I/O后端，借助`/dev/kvm`交互 | “KVM负责硬件辅助执行，QEMU负责用户态设备模型” |
| Xen | Xen Hypervisor负责基础CPU/内存隔离和VM执行；Dom0是具有管理能力的管理域，配合设备与管理服务 | “Hypervisor与Dom0职责分离” |
| Hyper-V | Hypervisor与分区机制；根分区提供管理和设备服务，子分区运行Guest | “根分区/子分区” |

**平台共同点：**都要解决CPU、内存、I/O三个基本问题；差别在于管理域、内核和用户态设备模型的组织方式，不能简单地把某一款产品归结为“没有Hypervisor”。〔第4章，P27–29〕

## 4.4 内存虚拟化：两级地址转换、EPT与Ballooning

**传统进程地址转换：**应用使用虚拟地址，由OS页表转成物理地址。虚拟机加入一个映射层，完整链路是：

`Guest Virtual Address (GVA) → Guest Physical Address (GPA) → Host Physical Address (HPA)`。

- **GVA→GPA：**Guest OS根据自身维护的页表完成转换；Guest以为自己拥有一片物理内存。
- **GPA→HPA：**Hypervisor/硬件辅助机制把Guest物理页映射到实际Host物理页。不同Guest可以使用相同的GPA编号，最终映射的HPA不同，以实现隔离。〔第4章，P19〕

**EPT（Extended Page Tables）：**Intel硬件辅助第二级地址翻译机制，负责**GPA→HPA**。课件以四级页表举例：EPTP指向顶级PML4；从GPA取不同位段逐级索引 PML4→PDPT→PD→PT；通常低12位为4KiB页内偏移，和最后找到的宿主页框地址拼接获得HPA。**EPT不是代替Guest自己的页表**，它处理第二级映射。〔第4章，P20〕

**内存超分配：**多台VM配置内存总额可超过宿主实际物理内存，在工作集不同时活跃时提高利用率；但若大家同时使用较多内存，可能产生内存压力甚至交换/性能下降。〔第4章，P21〕

**Ballooning（内存气球）：**当宿主需要回收部分内存时，Guest内部的Balloon Driver在虚拟机内“膨胀”，占用Guest可见的内存页，使Guest释放/减少对这些页的使用；Hypervisor据此回收对应宿主物理页。相反，气球“放气”可让Guest重新使用更多内存。**理解重点：内存回收通过Guest内的协作驱动，非凭空制造额外内存。**〔第4章，P21〕

## 4.5 I/O虚拟化：模拟、Virtio、直通、SR-IOV

| 技术 | 处理机制 | 优势 | 主要权衡 |
|---|---|---|---|
| Device Emulation 设备模拟 | QEMU等模拟传统网卡/控制器；Guest采用已有硬件驱动 | 高兼容性，便于运行老系统 | 模拟路径更长，CPU/VM Exit开销可能大 |
| Virtio 半虚拟化I/O | Guest前端Virtio驱动通过Virtqueue向后端提交请求/缓冲区，后端执行并回送完成 | 减少传统硬件模拟开销，适合虚拟机高效I/O | 需要Guest具备相应驱动与支持 |
| PCI Passthrough | 把物理PCIe设备直接映射给Guest使用，结合IOMMU进行DMA保护与映射 | 接近原生设备性能 | 设备独占，迁移/共享/管理受限 |
| SR-IOV | 单个支持SR-IOV的PCIe设备暴露PF（完整物理功能）和多个VF（轻量虚拟功能），可分别分配给VM | 在硬件支持下兼顾高性能与一定程度共享 | 受设备硬件、VF资源数量和迁移功能限制 |

**Virtio过程：**Guest应用发I/O→Virtio Front-end Driver组织请求→放入**Virtqueue**→Host后端处理真实I/O→完成通知/队列结果返回Guest。Virtio优化虚拟机I/O，不等于整个容器或GPU虚拟化。〔第4章，P22–23〕

**设备直通路径：**Guest驱动操作经映射的真实PCIe设备，DMA与中断等由硬件和虚拟化管理协同处理；IOMMU帮助限制设备DMA可访问的物理内存范围。并非所有设备都适合直接透传，因为独占与迁移会受到约束。〔第4章，P24〕

**PF/VF：**PF（Physical Function）拥有完整配置与管理能力；VF（Virtual Function）是从单块支持SR-IOV的设备中导出的轻量硬件功能。SR-IOV不是简单“把软件网卡复制多份”，而是有硬件设备支持的功能划分。〔第4章，P26〕

**常见选型：**老Guest兼容→设备模拟；通用云VM希望性能与可管理性兼顾→Virtio；高性能、专用硬件场景→Passthrough；要求高性能且硬件支持多VF→SR-IOV。四者的兼容性、隔离、共享、迁移和性能各有取舍。〔第4章，P25–26〕

## 4.6 存储虚拟化：分类、LVM、Thin Provisioning、Snapshot

**存储虚拟化：**在应用与SSD/HDD等物理介质之间引入映射/抽象层，以统一的逻辑卷、文件或对象接口交付存储，屏蔽后端设备差异。关键功能包括抽象、池化、映射与动态配置；虚拟化并不创造无限真实容量。〔第4章，P31〕

**按实现位置：**Host-based（主机侧，如Linux LVM）、Array-based（阵列控制器侧）、Network-based（网络层统一映射）。课件提醒不要与“带内/带外”这一不同分类维度混淆。〔第4章，P32〕

**LVM三层结构：**

`物理磁盘/分区 → PV（Physical Volume）→ VG（Volume Group）→ LV（Logical Volume）→ 文件系统/挂载`。

PV将底层设备纳入LVM；VG聚合多个PV形成空间池；LV从VG切出可使用逻辑卷，并在其上创建文件系统。PE（Physical Extent）是LVM在物理卷中组织可分配空间的单位。**扩容的逻辑：VG有空闲空间→LV扩容→文件系统按需增长**。〔第4章，P33〕

**Thin Provisioning（精简置备）：**向用户/VM呈现较大的**逻辑容量**，后端仅对实际写入的数据块分配物理空间，例如逻辑100GB卷尚未写满时可以只占用部分物理空间。收益是提高存储利用率；风险是物理池实际耗尽，必须监测容量与超分配程度。逻辑可见容量 **≠** 已消耗物理容量。〔第4章，P34〕

**Snapshot（快照）：**保存某一时间点的逻辑数据视图/块引用，通常不必创建时全量复制。COW（Copy-on-Write）常在首次修改共享旧块前保留旧内容；ROW（Redirect-on-Write）将新写入重定向到新位置。快照便于版本回退和短期保护，但**快照不是独立、可靠的异地备份**，也会有空间和性能开销。〔第4章，P35〕

**云硬盘访问链路：**`Guest文件系统/逻辑块地址 → 虚拟磁盘 → 虚拟化/卷映射 → 后端存储池 → 物理设备`。云平台控制层完成创建、扩容、挂载、快照、配额和备份等API管理。〔第4章，P36〕

## 4.7 网络虚拟化：vNIC、vSwitch、VLAN、VPN与接入模式

**定义：**将物理接口、交换、路由和网络连接抽象为租户可配置的逻辑网络，使多个租户共享物理基础设施但拥有独立网络拓扑和地址空间。〔第4章，P38〕

**虚拟网络的基本层次：**Guest操作系统及协议栈生成报文→vNIC（虚拟网卡）呈现MAC/IP等网络接口→vSwitch（虚拟交换机）进行本机端口的转发→物理NIC/交换网络提供外部连通。〔第4章，P39、P41〕

**vNIC与vSwitch区别：**vNIC是单个VM看到的网卡接口；vSwitch负责不同虚拟端口的本地转发和上联。若两个VM位于同一Host且在可互通的虚拟交换网络中，数据可以在本地主机内转发；若跨Host，必须穿越物理网络或使用相应Overlay隧道。〔第4章，P41、P43〕

**VLAN vs VPN：**VLAN使用802.1Q标签划分局域网二层广播域（VLAN ID是12位）；VPN通过共享网络形成逻辑专用连接/隧道，常用于跨网络连接和访问隔离。二者不是“VLAN在云里、VPN在本地”的区别。〔第4章，P40〕

| VM网络模式 | VM如何接网 | 外部主动访问 | 适用场景 |
|---|---|---|---|
| Bridge 桥接 | VM像局域网中独立节点接入已有网络 | 通常可直接连通（取决于网络规则） | 局域网服务与联调 |
| NAT | VM通过宿主NAT共享对外连接 | 通常需端口映射/特别配置 | VM主动访问互联网 |
| Host-only | VM与宿主/特定Host-only网络通信，不直接通外网 | 主要限于宿主与内部网络 | 本地隔离实验 |

**问“为什么两台VM通不了”**：考虑是否同一虚拟交换网络、VLAN隔离、IP/路由、防火墙、NAT规则、跨主机隧道及Underlay可达性，不能只检查VM是否有网卡。〔第4章，P42–43〕

## 4.8 Underlay/Overlay、VXLAN/VTEP、SDN/OVN

**Underlay：**真实物理网络及IP路由，目标是让各宿主/VTEP地址互相可达。**Overlay：**在物理承载网络之上构造租户的逻辑二层/三层网络和拓扑；同一个物理网络可承载不同租户的重叠私网地址。〔第4章，P44〕

**VXLAN原理：**VTEP（VXLAN Tunnel Endpoint）把Guest生成的原始以太网帧封装为外层IP/UDP/VXLAN报文，穿过Underlay，目标VTEP解封装恢复原始以太网帧。课件以**UDP目的端口4789**作为典型值；VXLAN Header中的**VNI**标记租户逻辑网络，外层IP地址决定Underlay如何路由。〔第4章，P45〕

**五步跨主机通信：**①VM1发送原始二层帧，本地vSwitch识别VNI；②查询或学习目标MAC所在远端VTEP；③源VTEP加Outer IP/UDP/VXLAN头；④Underlay按外层IP把封装包送至目的主机；⑤目的VTEP解封装，通过本地vSwitch交付目标VM。〔第4章，P46〕

**隔离思路：**不同租户即便都使用`192.168.1.0/24`，其VM只要处于不同VNI的逻辑网络，转发查找与隧道隔离仍可避免地址冲突。**VNI不是IP地址，也不承担实际物理路由。**〔第4章，P46〕

**SDN（Software Defined Networking）：**将网络**控制平面**（策略计算、路径/规则管理）与**数据平面**（实际转发）逻辑分离，控制器把网络配置下发到交换机/虚拟交换设施。三层理解为 Application Plane（业务/策略意图）→ Control Plane（计算配置）→ Data Plane（执行转发）。〔第4章，P47〕

**OpenStack Neutron + OVN：**Neutron提供网络、子网、端口、路由器、安全策略等云网络API；OVN负责将逻辑网络规则转换为相关控制/数据面行为；底层虚拟交换及网络节点实际转发。这是课件讲解“API交付—逻辑网络控制—数据包转发”职责边界的案例。〔第4章，P48〕

| 组件/技术 | 主要解决的问题 |
|---|---|
| vNIC/vSwitch | 单台Host内VM如何接入并交换数据 |
| VLAN | 传统局域网如何进行二层逻辑分段 |
| VXLAN/VTEP | 跨主机、跨三层承载网如何提供租户Overlay连通 |
| Underlay | 外层IP隧道的物理承载与路由可达 |
| SDN | 复杂网络规则如何集中编排、自动化下发 |
| Neutron/OVN | 云平台网络API如何落实到逻辑与实际转发 |

〔第4章，P49〕

## 4.9 容器虚拟化：Namespaces、cgroups、Docker与OCI

**VM vs Container：**VM虚拟化硬件并提供独立Guest内核；容器主要隔离共享同一个宿主Linux内核的进程环境，通常启动快、镜像小、资源开销较低；隔离边界与OS内核兼容需求不同。两者可叠加：一台云VM上运行多个容器。〔第4章，P52〕

**Linux Namespaces：解决“进程能看见什么”。**课件列出的典型隔离视图包括 PID（进程树/ID）、NET（网卡/地址/路由）、MNT（挂载点）、UTS（主机名等）、IPC（进程间通信）、USER（用户与身份映射）等。Namespacing重点是**环境视图隔离**，不是资源容量配额。〔第4章，P53〕

**Linux cgroups：解决“资源能用多少”。**针对CPU（时间配额与权重）、Memory（使用上限与回收）、I/O（带宽/权重）、PIDs（进程数）等进行资源控制，限制容器相互抢占。Namespaces+cgroups共同提供容器的隔离与控制基础，还需文件系统、运行时及安全机制形成完整容器环境。〔第4章，P54–55〕

**Docker核心对象：**Image（只读镜像模板）、Container（运行实例）、Dockerfile（构建说明）、Registry（镜像仓库）、Docker Engine/Daemon（构建和运行管理）。Docker解决可重复打包、分发和运行，不是Namespaces/cgroups本身的发明。〔第4章，P56〕

**执行 `docker run` 的职责链：**Docker CLI→Docker Daemon→containerd→runc/OCI Runtime→Linux Namespace/cgroups等机制启动容器进程。**containerd负责生命周期/镜像管理，runc负责按OCI运行规范创建底层容器进程。**〔第4章，P57〕

**OCI标准与镜像分层：**OCI Image/Runtime规范使不同实现兼容；容器镜像由多个只读层组成，运行时添加可写层并借助写时复制（Copy-on-Write）降低重复存储和分发成本。**镜像并非在每次启动时复制所有只读层。**〔第4章，P58〕

## 4.10 GPU虚拟化、VDI与现代云协同

| GPU技术 | 基本方式 | 优势 | 权衡/适用 |
|---|---|---|---|
| GPU Passthrough | 整块GPU直通给一个VM | 性能强、访问接近原生 | GPU独占、共享效率可能低 |
| vGPU | 通过厂商/虚拟化机制共享物理GPU | 多租户共享、提高利用率 | 资源干扰、软件/授权及隔离依赖实现 |
| MIG | 支持的GPU进行硬件空间分区，形成具备资源边界的实例 | 较明确的计算/显存分区 | 依赖特定硬件及分区能力 |

**GPU选择取舍：**看性能隔离、显存需求、资源利用率、任务规模与硬件支持，不是“任何GPU都能MIG”。〔第4章，P59〕

**VDI（Virtual Desktop Infrastructure）：**将桌面OS与应用运行在数据中心，用户终端主要负责显示和输入；涉及访问网关、身份认证、桌面管理平台和远端桌面实例。优势是集中管理与交付，代价包括网络体验、数据中心容量及用户外设/图形性能适配。〔第4章，P60〕

**技术分工总结：**虚拟化提供可隔离的资源运行单元；IaaS提供供给、计量、运维和API交付；Container提供轻量标准化应用交付；Kubernetes提供大规模编排；GPU虚拟化支持智能算力共享。现代云通常是这些能力协同，而不是“容器已经淘汰VM”。〔第4章，P61–62〕
